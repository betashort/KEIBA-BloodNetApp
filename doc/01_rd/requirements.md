# 要求仕様・要件

## 1. 目的

競走馬の血統情報をグラフとして保持し、探索・可視化・分析を容易にする基盤を作る。

### 1.1 ゴール

1. 任意の馬を起点に、父・母・祖先をグラフとして辿れる
2. 5代血統表を中心とした血統ビジュアライズができる
3. インブリード（クロス）、母系、系統など血統分析に必要な関係を機械的に抽出できる
4. PostgreSQL 等の既存／蓄積データをソースに、グラフへ再現可能な形で載せられる

### 1.2 非ゴール（初期スコープ外）

- 出走予想・オッズ予測そのものの実装
- リアルタイム配票・投票連携
- 血統以外の全競馬ドメイン（騎手・厩舎・レース結果の詳細分析）の完全網羅  
  ※ノード／リレーションとして拡張可能な設計は要件に含めるが、初期実装は血統中心

---

## 2. 想定ユーザー

| ユーザー | 主な関心 |
| -------- | -------- |
| 開発者／データ分析者 | データ投入、Cypher／API での探索、モデル拡張 |
| 血統分析利用者（自分／将来の一般ユーザー） | 血統表閲覧、クロス確認、系統・母系の把握 |
| （将来）一口馬主・競馬ファン | 出資候補馬の血統比較、兄弟・母系活力の確認 |

初期は開発者・分析者向けの運用を優先し、一般向け UI の完成度は段階的に上げる。

---

## 3. 機能要件

優先度: **Must**（必須）／ **Should**（できれば）／ **Could**（将来）

### 3.1 データ管理

| 要件 | 優先度 |
| ---- | ------ |
| 馬を一意に識別し、ノードとして登録・更新できる | Must |
| 父・母の関係をリレーションとして保持できる | Must |
| 馬の基本属性（名称、性別、生年 等）を保持できる | Must |
| PostgreSQL（または同等のマスタ）からグラフへ初期投入できる | Must |
| 差分同期または再投入により、グラフを最新化できる | Should |
| データ品質チェック（孤児ノード、父母欠落、循環 等）ができる | Should |
| 種牡馬／繁殖牝馬／号族など分析用ラベル・属性を付与できる | Should |

### 3.2 血統探索

| 要件 | 優先度 |
| ---- | ------ |
| 指定馬から N 代祖先（既定 5 代）を取得できる | Must |
| 父系（父→父父…）を辿れる | Must |
| 母系（母→母母…）および母父（BMS）を辿れる | Must |
| 指定世代内の共通祖先（インブリード／クロス）を検出できる | Must |
| クロス結果を「祖先名 × 世代表記（例: 4×4）」で表現できる | Must |
| 指定祖先の子孫集合を取得できる（産駒・系統展開） | Should |
| 2 頭間の血統距離・共通祖先パスを取得できる | Should |
| 系統クラスタ／類似馬探索（GDS 等） | Could |

### 3.3 可視化

| 要件 | 優先度 |
| ---- | ------ |
| 指定馬の 5 代血統表を表示できる | Must |
| 血統表上で父側／母側が視覚的に区別できる | Must |
| クロス対象祖先を血統表上でハイライトできる | Must |
| グラフ探索ビュー（ノード・エッジの拡大縮小・パン）で祖先を辿れる | Should |
| 馬詳細（属性・父母リンク）をサイドパネル等で確認できる | Should |
| 馬名・ID による検索から可視化へ遷移できる | Must |
| 母系ライン／号族ビュー | Could |
| 系統勢力図・クラスタ可視化 | Could |

### 3.4 API／連携（実装形態は問わない）

| 要件 | 優先度 |
| ---- | ------ |
| 馬検索（名前部分一致・ID）ができる | Must |
| 血統ツリー（N 代）を構造化データで返せる | Must |
| クロス一覧を構造化データで返せる | Must |
| 可視化フロントが上記を消費できる | Must |
| Neo4j Browser／Bloom 等の管理系 UI でも直接確認できる | Should |

### 3.5 分析支援（血統分析観点との対応）

血統分析で重視する観点（距離適性・馬場適性等）の**数値そのものの算出**は初期必須ではないが、グラフ上で次を満たすこと。

| 要件 | 優先度 |
| ---- | ------ |
| 父／母父／3 代以内クロスを機械抽出できる | Must |
| 兄弟・半兄弟の列挙ができる | Should |
| 種牡馬成績・BMS 成績等を将来接合できる拡張点を持つ | Could |
| レース成績・距離／馬場別集計との接合（PG 側集計＋グラフ ID 連携） | Could |

---

## 4. 非機能要件

| 分類 | 要件 |
| ---- | ---- |
| 性能 | 単一馬の 5 代血統取得がインタラクティブに応答すること（目安: 数百 ms〜数秒以内、データ規模に依存） |
| 性能 | クロス検出（5 代内）が実用時間内に完了すること |
| スケール | 少なくとも国内サラブレッド中心の馬マスタ規模（数十万ノード級）を想定した設計とすること |
| 再現性 | ETL／投入手順が文書化され、同一ソースから再構築可能であること |
| 整合性 | 馬 ID を PostgreSQL と Neo4j で突合可能なキーとして維持すること |
| 運用 | ローカル Docker 等で開発環境を立ち上げられること（手順: [../02_design/environment.md](../02_design/environment.md)） |
| セキュリティ | 認証情報をリポジトリに含めないこと。初期はローカル／閉域想定 |
| 拡張性 | レース・騎手・調教師などのノード追加がスキーマ破壊なしで可能であること |
| 可用性 | 初期は単一インスタンスで可。高可用性は対象外 |

## 5. データ要件

詳細は [../02_design/data_model.md](../02_design/data_model.md) を参照。

### 5.1 必須エンティティ

- **Horse（馬）**: 識別子、名称、性別、生年 等
- **親子リレーション**: 父・母（方向・意味が一意であること）

### 5.2 必須に近い属性・メタ

- 外部キー相当の安定 ID（例: `horse_id`）
- 表示名（日本語名を優先、英名は任意）
- 性別（牡／牝／セン 等）

### 5.3 ソースデータ前提

- 一次ストアは PostgreSQL（または同等）を想定
- グラフは派生ストアとし、血統探索・可視化の正とする
- レース結果・集計は当面 PostgreSQL に残し、必要に応じて参照連携

### 5.4 品質ルール

- 同一馬の重複ノードを作らない（MERGE キーの明確化）
- 父母が不明な場合は欠落を許容し、可視化で欠損表示する
- 循環（自己祖先）は検出・報告する

---

## 6. 制約・前提

1. データソースの利用規約・再配布制限を遵守する（公開データの取り扱いに注意）
2. グラフDB は当面 Neo4j を第一候補とする（調査メモ準拠）。代替検討は設計フェーズで可
3. UI 技術スタックは未確定。要件は技術非依存で記述する
4. 「血統で成績が決まる」ことは主張せず、分析支援ツールとして位置づける

---

## 7. 受け入れ基準（初期 MVP）

次をすべて満たせば初期 R&D／MVP 完了とみなす。

1. 馬マスタと父母関係が Neo4j に投入されている
2. 任意の登録馬について 5 代血統表を表示できる
3. 5 代内クロスを検出し、血統表上でハイライトできる
4. 馬名検索から上記表示に到達できる
5. PostgreSQL → Neo4j の投入手順が再現可能である

- 海外馬・抹消馬・繁殖専用馬のカバレッジ
- 公開 UI の有無と認証方式
- Bloom／自前 UI／既存グラフ可視化ライブラリの選定
- リアルタイム同期の要否（バッチで足りるか）
